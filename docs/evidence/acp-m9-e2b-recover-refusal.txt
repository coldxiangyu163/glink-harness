机制（为什么这构成“真实回收失败 → 追问拒绝”）
------------------------------------------------
1. 真实宿主 + 真实沙箱跑一次父 run（dsh + 真实模型）。
2. 回合进行中（session_ready 已出现、run 仍 running），探针用真实 SDK
   `Sandbox.connect(sandbox_id)` 连到**同一个沙箱**，用沙箱内命令把合成大文件写进其 ACP
   状态根（`/home/user/acp/home/bloat.bin` = 9437184 B > 单文件上限 8388608 B）。文件不
   经宿主上传通道，所以能超过 e2b 上传上限而仍落在状态根里。
3. run finalize 调用**生产回收函数**（e2b 面 `recover_state()`）：它整份拒绝、不发布
   `recovered` 根，并把原因写进终态帧 `artifactFailures`。
4. 以该 run 作父再 POST `/api/runs`（`parentRunId`）：准入层读不到父状态根，按
   `session_unavailable` 拒绝（HTTP 409），**在起沙箱之前**，不预支一次注定失败的云端 run。

缺陷：探针把“父 run 记录了 resume 能力位”写成
`capabilities["sessionCapabilities"]["resume"] is True`，而 dsh 的真实能力矩阵是
`{"close": {}, "list": {}, "resume": {}}`——resume 位是**存在**（空对象），不是布尔 true；
宿主自身用生产函数 `acp_resume_method()` 判定，所以真正的准入条件已经满足，只有探针这一条
自检判据错。修复：改用同一个生产函数 `acp_resume_method(capabilities) == "session/resume"`。
