已知差异（如实记录）
--------------------
1. **协议**：E2B SDK 不提供双向 stdio，这一面用 `pi --mode json "<prompt>"` 的单向事件流，
   而不是 RPC 协议（objective 中写明的协议退回路径）。prompt 与研究约定经 base64 传递，
   避免 shell 引号问题。
2. **事件时序**：e2b 2.x 的 `commands.run(background=True, on_stdout=…)` 回调**实测不触发**
   （`handle.wait()` 的返回值里只有最终 stdout）。因此沙箱把事件写成
   `/home/user/events.jsonl`，宿主在命令结束后一次性回放。事件的顺序、内容与词汇与其他
   两面一致，差别是**非实时**。
3. **会话持久化**：pi 的会话文件写在沙箱内 `/home/user/sessions`，随沙箱销毁而消失，
   因此 E2B 面的 run 元数据里 `session_id` 为空。宿主的 run 记录与报告仍然持久。

更正注记（GLINK-E2B-LIVE-01）
------------------------------
本文「已知差异 2. 事件时序」的结论已被更正：e2b 2.x 的
`commands.run(background=True, on_stdout=…)` 回调不触发是**用法误判** ——
background=True 的重载不消费 `run()` 上的回调（类型即 None），流式接口是它返回的
`CommandHandle`（`__iter__` 逐块产出 stdout/stderr/pty，`wait(on_stdout=…)` 逐块回调），
且当时 pi 的 stdout 被重定向进文件，本就没有数据可流。宿主现已在命令运行期间迭代
handle，把 pi 的 stdout 同时 `tee` 到 `/home/user/events.jsonl`，按 LF 逐行实时投递；
流中途断开时按文件补发「已送出行数」之后的帧（命令在管道后写退出码标记文件），
不漏不误。宿主侧离线验证完成；真实 E2B live 实时性待另行授权复验。
