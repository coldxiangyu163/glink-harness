结论（逐轴）
------------
* control：ok=true，2 文件 / 30 B，发布 state-a.json 与 sub/state-b.txt，发布内容 sha256
  与沙箱内合成内容一致 → 回收路径本身可用，失败不是“路径坏了”。
* single（轴 1，单文件）：ok=false，
  failures=["沙箱状态文件不可读取或超过上限: bloat.bin: 文件超过上限（9437184 > 8388608 字节）"]，
  0.23s；宿主无 recovered / 无 staging；沙箱内状态 2 文件 / 9437211 B 前后一致。
* total（轴 2，总量）：ok=false，failures=["沙箱状态超过总量上限 67108864 字节"]，3.74s；
  沙箱内 10 文件 / 75497501 B 前后一致；每个文件都在单文件上限内（8388608 B）。
* count（轴 3，文件数）：ok=false，failures=["沙箱状态文件数超过上限 4096"]，
  1026.73s；沙箱内 4100 文件 / 0 B 前后一致。该轴也是 listing 规模的实测：一次
  `files.list(depth=12)` 完整返回 4101 条目（4100 文件 + 1 目录）。
* 三条轴的共同事实：拒绝时 `recovered` 与 `.recovered.staging` 都不存在（**不留半份**），
  拒绝原因在 verdict `failures` 里可读（**事实可观测**），沙箱按 id 终止
  （`confirmed_absent=True`，`SDK 确认沙箱不存在`）。

真实 SDK 形状与风险（`e2b 实测`）
--------------------------------
* 真实 SDK 的递归 listing 条目带 `size`（`EntryInfo.size`；目录条目也有 size），所以
  单文件轴走元数据预检、不必先读满再拒——`_read_file_bounded` docstring 里“真实 SDK 的
  size/stream 形状待实测”这一条由此闭合（对应 §14.1 与 §15.2）。
* 文件数轴的处理代价是**逐文件一次流式读取**：实测 4096 个空文件 1026.73s（约 0.25s/文件）。
  本次沙箱寿命为 `LOCAL_WEB_TASK_TIMEOUT_SECONDS=900` → `900+300=1200s`，即该轴在寿命
  内只剩约 3 分钟余量。若按默认任务超时 300s（寿命 600s）跑同一状态根，读会在沙箱到期时
  失败——结论仍是 fail-closed（不发布 recovered 根、追问被拒），但拒绝原因会变成读失败
  而不是“文件数超过上限”。这是当前“整份镜像”设计在长会话逼近文件数上限时的已知代价，
  记录在 §15.2/§15.5，未在本任务改动行为。
