凭据边界证据 / credential boundary evidence
============================================
日期: 2026-09-22
背景: 独立审计驳回指出——OPENAI_API_KEY 被注入 pi 进程环境（bash 工具可继承）、
      工具输出/报告/会话文件未脱敏、用虚拟密钥构造的 tool_execution_end 帧可原样穿过投影。
      本文件记录两条修复线的证据：① key 不进进程环境；② 出站六层脱敏。

① key 不进进程环境（本次返工）
-------------------------------
做法:
  * 宿主渲染两份运行期文件：models.json（literal baseUrl/model id，**不写 apiKey**）与
    auth.json（pi 官方凭据存储，`/login` 写的同一个文件，权限 0600，位于仓库外）。
  * build_pi_env 只放行白名单环境变量（PATH/HOME/代理/证书等）并注入 PI_*，不再注入
    OPENAI_API_KEY；docker 面移除 `-e OPENAI_API_KEY`；e2b 面把 auth.json 上传到
    /home/user/config/ 而不是经 envs 传 key。
  * 实测确认 pi 对自定义 provider（frontier）会从 auth.json 取凭据：
    `env -u OPENAI_API_KEY PI_CODING_AGENT_DIR=<runtime> pi --list-models`
    输出 `frontier  openai/gpt-5.6-sol  128K …`。

运行期文件（一次真实 run 后）:

  ~/.pi-glink/pi-agent/auth.json     134 B, {"frontier": {"type": "api_key", "key": "<redacted>"}}, 0600

⑤ fail-closed 投影与 prompt 脱敏（最终收口）
---------------------------------------------
  kernel/projection.py
    project_event(frame) 未传 redactor 时改用模块级 _FALLBACK_REDACTOR（形状检测）：
    “忘记传 redactor”只会降低检测能力（宿主已知值匹配不到），不会变成泄漏。
    这正是审计复现用例的最窄调用形态（tool_execution_end + OPENAI_API_KEY=…）。
  kernel/runner.py
    用户可把凭据粘进 prompt：落盘/展示的副本先脱敏，原始指令经 _Execution.kernel_prompt
    单独送给内核（RPC 面与 E2B 面都走 kernel_prompt），因此用户指令不被改写、
    meta.json 不持久化粘贴的凭据。
  新增回归:
    test_projection_without_an_explicit_redactor_is_fail_closed
    test_pasted_credential_in_the_prompt_is_not_stored_in_metadata
    （连同 ④ 的两项，tests/test_redaction.py 共 17 项）
  回归: Python 95 项 + Node 11 项全绿；扫描器 真实命中 0 / 占位符 2
