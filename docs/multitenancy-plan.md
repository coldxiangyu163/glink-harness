# 多租户下一阶段方案（决策提案）

[架构](architecture.md) · [工程约束](engineering.md) · [pi 边界](pi-boundary.md)

这份文档把「通过 Docker / E2B 独立执行环境支持多租户研究」拆成可实施的阶段，并标出
**当前已实现**、**下一阶段可在取得决定后实施**、**必须由产品/运维先裁决**三部分。它不是
上线验收：本文里的任何一项在未取得对应决定与验收证据前都不代表已经交付。

## 1. 当前基线（已经实现，可在其上演进）

| 能力 | 现状 | 复用点 |
|---|---|---|
| Run 生命周期 | `RunManager` 管理单 run 槽；结论与取消在同一线性化点裁决并以终帧提交；准入由「执行中 run + 未确认释放的资源台账」导出 | 后续调度只替换「准入/排队」的容量模型，不改 Run 语义与提交点 |
| 执行面抽象 | `ExecutionAdapter`（`start/session_info/deliver_input/wait/recover_artifacts/close/identity`） | 新执行面/多宿主机只需新适配器 |
| 每 run 独立环境 | 运行期配置与产物副本在 `runs/<id>/`，session 在会话根下的 `<id>/`，工作区在 `workspaces/<id>/` | 租户隔离的天然边界，待加 owner 标签 |
| 持久事件 | `events.jsonl` 为提交事实源，先落盘再发布，支持 `Last-Event-ID` 重放；终帧即终态提交，`meta.json` 终态字段是落定副本 | 多宿主演进时成为 outbox/事件源 |
| 产物安全 | 内核可达文件经目录句柄逐级不跟随链接读写；报告复制到宿主拥有的 `artifacts/`；下载只认宿主产物与旧版本工作区报告两个固定位置 | 下载与清理只认校验过的宿主路径 |
| 凭据与脱敏 | 每 run 的 `auth.json`/`web-search.json`（0600），出站值+形状+跨 delta 脱敏 | 单机回显保护；不构成租户级凭据隔离 |
| 外部资源身份 | `container_name` / `sandbox_id` 持久化；取得 `data_root` 独占所有权后 `reconcile()` 才收口遗留 run；未确认释放的资源持续占用容量，只能人工裁决放行 | 租约/对账的持久锚点 |

**尚未实现**：可信租户身份与授权、任何 owner 校验、并发准入与配额、跨宿主存储、per-tenant
凭据代理、跨租户拒绝验收。当前服务默认只绑 loopback，且同一时间只允许一个 run。

## 2. 租户身份与所有权（下一阶段，需先决定认证入口）

### 2.1 可信 TenantContext

TenantContext 必须来自**服务端可信入口**，不能来自请求体、查询参数或前端存储：

1. 推荐形态：宿主部署在认证代理/网关之后（OIDC/SAML/mTLS 由网关完成），网关注入不可伪造的
   身份头（如 `X-Auth-Request-Sub`、签名 JWT），宿主只接受来自网关且已配置的信任链；
2. 若宿主直接对外，则需要内置 session/JWT 校验与登录入口——这会引入凭据存储、会话管理和
   前端登录流程，属于产品决定（见 §8-D1）；
3. TenantContext 至少包含 `tenantId`、`userId`、`roles`、`requestId`，并在启动时冻结校验参数
   （issuer/audience/公钥缓存策略），与当前 `HostConfig` 的冻结方式一致。

### 2.2 所有权模型

每个 run 及其派生物都有 owner，所有读取面按 owner 过滤而不是「先查再判断」：

| 对象 | 归属字段 | 强制点 |
|---|---|---|
| run 记录 | `tenant_id` / `user_id` | 列表、详情、启动、取消 |
| 事件流 | 继承 run | SSE 订阅、`Last-Event-ID` 重放 |
| 产物/报告 | 继承 run | 下载、清理；路径仍限制在 run 目录内 |
| 会话文件 | 继承 run | 只在本次 run 的会话子目录内读改写 |
| 执行资源 | 继承 run | `container_name`/`sandbox_id` 的取消与回收 |
| 凭据 | 继承 run | 每 run 的运行期目录；租户级凭据见 §6 |

实现方式：`RunStore` 的查询方法接受 TenantContext 并返回/过滤 owner；`RunManager` 在
`start/stop/wait` 与事件订阅入口校验；产物下载与 SSE 都在服务层校验。跨租户请求统一返回
`404`（不泄露存在性）或 `403`（已授权入口但角色不足），两种口径需在决定后固定。

### 2.3 取消、下载与清理的跨租户拒绝

取消不是「按名字杀容器」：只有 owner（或带审计的运维角色）能取消；回收只使用 run 记录里
持久化的资源身份，且校验该身份属于本次取消的 run（当前 `_Execution`/`identity()` 已提供）。
跨租户尝试必须被拒绝且留审计事件，不得静默失败。

## 3. 存储演进（单机事务 → 多宿主）

### 3.1 单机事务存储（推荐先做）

当前 `RunStore` 是文件实现：`meta.json` 原子替换、`events.jsonl` 追加。它已经满足「先提交后
发布」，但缺少跨文件事务与并发写保护：

- 推荐：单机切到 SQLite（WAL）事务库：`runs` 表（owner/status/身份/终态字段）、
  `events` 表（run_id, seq, type, payload, ts，唯一键 `(run_id, seq)`），产物与会话仍在
  文件系统，用相对路径引用。事件提交与 `event_count` 在同一事务里完成，天然满足当前
  「提交成功点、seq、实时通知、最终计数一致」的承诺。
- 迁移方式：首次启动时扫描现有 `runs/` 目录导入一次，保留原文件只读；导入失败不阻塞新 run。
- 决策点见 §8-D3（是否现在换、是否允许历史导入写回）。

### 3.2 多宿主演进点

单机事务库不能跨机器共享状态，多宿主要求：

1. 共享数据库（推荐 Postgres）+ 对象存储（报告/产物/会话）；
2. 事件发布改为 outbox 模式：事务内写 `events`，后台投递到共享流（Redis Streams / NATS /
   Kafka 之一）供多宿主 SSE 与对账；`seq` 仍按 run 单调，由数据库分配；
3. 调度改为「租约 + 心跳」：run 记录带 `owner_host`、`lease_expires_at`、`fencing_token`；
   宿主拿到租约后才能启动执行面，心跳丢失则由其他宿主接管对账（不接管运行中的执行面，
   而是按策略终止/回收后标记 `interrupted`）；
4. 产物路径从本地绝对路径改为对象存储 key，下载走签名 URL 或宿主代理。

这些都属于「取得决定后实施」的范围，本文不选型数据库供应商，也不定义生产迁移窗口。

## 4. 并发准入、配额与资源回收（下一阶段）

当前三面共享全局单 run 槽。并发开放的前置条件（缺一不可）：

1. **可信 owner**（§2）——否则并发只是扩大越权面；
2. **准入与配额**：按租户（以及可选按用户）限制并发 run 数、排队上限、单 run 墙钟与 token
   预算；超出返回可解释的 `429/409`，不排队到无限；
3. **每 run 资源上限**：Docker 的 cpu/memory/pids、E2B 模板的资源与超时；宿主记录并核对
   实际用量；
4. **持久执行身份 + 租约**（§3.2）保证中断可对账；
5. **回收策略**：终态后销毁执行面、释放槽位；孤儿资源只通过持久身份做**有界**对账
   （列出 + 明确批准后回收），不自动扫描或终止未知资源。

inproc 面保持单 Agent 调试入口，不因并发支持而取消全局安全保护来「看起来像多租户」。

## 5. 中断恢复语义（下一阶段）

需要固定的语义（当前已实现单机版本的一部分）：

| 场景 | 语义 | 现状 |
|---|---|---|
| 宿主进程退出，run 未终态 | 新宿主取得 `data_root` 独占所有权后对账为 `failed/interrupted`，附外部身份，资源状态记为未知；已提交终帧的 run 只落定、不改写 | 已实现（单机：`host.lock` + `reconcile()`） |
| 同一数据目录启动第二个宿主 | 在对账前以 `DataRootBusy` 拒绝，不改动活跃 owner 的 run | 已实现（单机本地文件系统 `flock`；不是多宿主租约） |
| 执行面资源仍存在或状态未知 | 不自动销毁；持续占用容量，新 run 返回 `409 resources_unreleased`；`--unreleased` 列出、`--mark-released` 人工裁决后放行 | 已实现（单机） |
| 多宿主租约过期 | 接管方按策略终止执行面并标记 `interrupted`，写入接管审计 | 未实现 |
| 取消请求与终态竞争 | 取消与结论在同一线性化点裁决：提交前受理的取消必为 `cancelled`，提交后的取消返回 `409` 与已提交状态 | 已实现（单机） |
| 事件流断线 | 客户端按 `Last-Event-ID` 从持久日志补齐 | 已实现（单机） |

## 6. 凭据策略（下一阶段，需产品决定）

现状：每 run 独立 `auth.json`/`web-search.json`，密钥由宿主启动配置提供并被出站脱敏保护。
多租户要求：

- **推荐**：宿主不再保存租户的长期模型密钥，而是为每个 run 申请短期、限额、可审计的凭据
  （云厂商 STS/凭证服务，或宿主侧凭据代理：内核只拿短期 token，代理持有长期密钥并限流/记录）；
- 租户级与 run 级凭据归属、额度、轮换与吊销策略需要决定；
- 搜索凭据同理（每租户/每 run 独立，缺失时回退无密钥检索）；
- 高权限凭据代理或短期令牌服务属于**新增部署组件**，本次不实现、不偷偷上线；只在本方案中
  给选项与推荐。

## 7. 历史数据归属与迁移（需决定）

当前数据是单用户形态：`~/.pi-glink/runs/<id>/`、`workspaces/<id>/`，记录里没有 owner。
可选方案：

| 方案 | 说明 | 回退 |
|---|---|---|
| A（推荐）默认租户回填 | 迁移时把所有历史记录归到配置里的「本地默认租户」，用户可见历史不中断 | 保留原目录只读副本；回填只写新库 |
| B 显式导入 | 历史保持在旧目录只读，按需导入到某租户 | 不导入即回到旧行为 |
| C 只读保留 | 历史仅本机可见，不进入租户视图 | 不做迁移，零风险 |

无论哪种，都**不删除**用户历史（`events.jsonl` 不因 TTL 清理）；迁移脚本必须可重入、可断点、
有干跑模式，并在决定后单独验收。

## 8. 需要用户/产品裁决的具体问题

- **D1 认证入口**：（a）网关/企业 OIDC（推荐，宿主只信任注入头）；（b）宿主内置登录；
  （c）仅本地单用户、不加认证。选择 (a) 需要确定 issuer/audience/信任链与网络边界。
- **D2 租户粒度与并发**：租户内的用户是否独立配额？单租户默认并发（建议首发 2，可配置）
  与全局上限？队列还是立即拒绝（建议立即拒绝 + 可重试语义）？
- **D3 存储**：是否现在切 SQLite（推荐，单机即可获得事务性与 owner 字段）；何时引入
  Postgres/对象存储；是否允许自动导入历史数据。
- **D4 凭据**：是否建设短期凭据代理/STS；每租户每月额度与告警阈值；是否允许租户自带密钥
  （BYOK）以及如何审计。
- **D5 历史迁移**：选 §7 的 A/B/C；若选 A，默认租户 id 与显示名。
- **D6 开通流程**：租户如何创建与停用；停用后并发 run、事件流与产物下载的处置口径。
- **D7 审计与合规**：审计事件保留期、导出格式、谁可读；是否需要数据驻留与删除请求支持。

## 9. 验收（取得决定后）

1. **跨租户拒绝矩阵**：列表、详情、事件流、报告下载、取消、启动、凭据读取——每项都有
   正例（owner）与反例（另一租户），反例返回统一状态码且无数据泄露；
2. **并发与配额**：达到租户/全局上限时的行为、排队拒绝路径、资源用量记录；
3. **恢复演练**：宿主重启、租约过期、执行面残留、取消竞争，逐项给出诚实终态与资源处置；
4. **凭据隔离**：租户 A 的 run 无法读取租户 B 的配置/凭据/会话/产物；短期凭据到期后的失败
   路径可解释；
5. **负载验收**：N 租户 × M 并发 run 的稳定运行、事件延迟与存储增长；不在本方案宣称的
   容量数字内上线。

## 10. 明确不做

- 不在本次交付中启用并发、远程多用户、认证代理、数据库或对象存储；
- 不选型认证供应商、计费价格、生产数据库或迁移窗口；
- 不把本方案当作上线验收，也不把「单机隔离测试通过」当作多租户已经安全。
